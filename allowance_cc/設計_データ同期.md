# データ保存方式の変更 設計書(Google スプレッドシート同期)

- **作成日**: 2026-09-07
- **ステータス**: 実装済み(2026-09-07)。保護者のセットアップ待ち
- **セットアップ手順**: `同期セットアップ手順.md`
- **対象**: `index.html` / 新規 Apps Script

---

## 1. 背景と目的

現状はデータを `localStorage` のみに保持しており、以下の弱点がある。

- ブラウザの履歴削除や iOS のストレージ自動削除でデータが消える
- 復旧は保護者の**手動バックアップ運用に依存**する(30日ごとの催促バナー頼み)
- 保護者がデータを見るには、子どものiPadを借りて暗証番号を入力する必要がある

これを Google スプレッドシートへの保存に変更したい、というのが今回の要望。

### 1.1 真の要件

「スプレッドシートに保存すること」自体は目的ではなく、手段である。
本質的な要件を分解すると次の3点になる。

| # | 要件 | 現状 | 重要度 |
|---|---|---|---|
| R1 | 端末やブラウザのデータが消えても記録が失われない | 手動バックアップ頼み | **必須** |
| R2 | 保護者が自分の端末からいつでも状況を確認できる | 子のiPadが必要 | 高 |
| R3 | 保護者の運用努力(定期バックアップ)なしで R1 が満たされる | 満たせていない | 高 |

加えて、**譲ってはいけない制約**が3つある。

| # | 制約 | 理由 |
|---|---|---|
| C1 | 子どもに Google ログインをさせない | 13歳未満のGoogleアカウントは Family Link 必須。運用が破綻する |
| C2 | オフラインでも即座に記録できる | 小3の利用シーンで通信待ちや通信エラーを見せない |
| C3 | 追加費用が発生しない | 家庭内利用のため |

## 2. 方式の比較検討

| 方式 | 子のGoogleログイン | オフライン動作 | 初期設定の重さ | 自動復元 | 費用 | 評価 |
|---|---|---|---|---|---|---|
| **A. localStorage を主 + Apps Script でシート同期** | 不要 | ○ | 中(保護者10分) | ○ | 無料 | **採用** |
| B. Sheets API をブラウザから直接利用(OAuth) | **必要** | × | 大 | ○ | 無料 | 却下 |
| C. スプレッドシートを唯一の保存先にする | 不要 | **×** | 中 | ○ | 無料 | 却下 |
| D. Firebase Firestore(匿名認証) | 不要 | ○ | 中 | **×** | 無料枠 | 却下 |
| E. Google フォーム送信で追記のみ | 不要 | ○ | 小 | **×** | 無料 | 補助的 |
| F. 現状維持(手動バックアップのみ) | 不要 | ○ | なし | × | 無料 | 現状 |

### 2.1 各案の評価

#### B. Sheets API を直接利用(OAuth)— 却下
一見もっとも素直だが、**C1 に真正面から抵触する**。

- スプレッドシートに書き込む主体が子どもの端末になるため、**子ども自身が Google にログインする必要がある**
- アクセストークンの有効期限は約1時間。ブラウザのトークンフローではリフレッシュトークンが得られず、
  期限切れのたびに再同意が必要になる
- OAuth 同意画面が「テスト」状態のままだと、トークンが数日で失効する。
  回避するにはアプリ審査(verification)が必要で、家庭用アプリには過大
- 未検証アプリの警告画面を子どもが突破する運用になり、教育上も望ましくない

#### C. スプレッドシートを唯一の保存先にする — 却下
**C2 に抵触する。** 記録のたびにネットワーク往復(数百ms〜数秒)が発生し、
電波の悪い場所ではアプリが機能しない。「おこづかいを記録する」という
1日数十秒の操作に対して、通信エラーのリスクを子どもに見せる設計は不適切。

#### D. Firebase Firestore(匿名認証)— 却下
技術的には最も洗練されている(オフライン永続化・リアルタイム同期が標準装備)が、
**匿名認証のユーザーIDはブラウザのストレージに保存される**。
つまりストレージが消えると自分のデータへのアクセス権ごと失われ、**R1 を満たせない**。
これを解決するには実名認証が必要になり、結局 B と同じ問題に行き着く。
また利用者が「データベースを持たない方法」を希望している点にも反する。

#### E. Google フォームへの送信 — 補助的な位置づけ
Google フォームの送信エンドポイントは認証なしでクロスオリジン POST を受け付けるため、
**設定が最も軽い**(フォームを1つ作るだけ)。送信内容は自動的にスプレッドシートに追記される。

ただし `no-cors` 送信のため**成功可否すら取得できず、読み戻しもできない**。
自動復元(R1)を満たせないため主方式にはできない。「万一のための追記専用の証跡」としてなら有効。

## 3. 採用方式:ローカル優先 + スプレッドシート同期(ハイブリッド)

### 3.1 基本方針

> **`localStorage` を「正」とし、スプレッドシートは常に最新の内容が複製される「鏡」とする。**

- アプリの動作は現状と変わらない(即応・オフライン可)
- 変更のたびに、バックグラウンドで**全データのスナップショット**をシートへ送る
- 端末のデータが消えたら、シートから引き戻して復元する
- 同期に失敗してもアプリは一切止まらない(子どもには何も見せない)

### 3.2 構成図

```
   ┌─────────────────────────────┐
   │  子どものiPad (index.html)    │
   │                              │
   │   localStorage  ← 正・即応     │
   │        │                     │
   │        │ 全件スナップショット     │
   │        ▼ (5秒デバウンス)        │
   └────────┼─────────────────────┘
            │ HTTPS POST (JSON)
            ▼
   ┌─────────────────────────────┐
   │  Google Apps Script (Web App) │
   │  「保護者のアカウントとして実行」  │
   └────────┼─────────────────────┘
            ▼
   ┌─────────────────────────────┐
   │  スプレッドシート(保護者のDrive) │
   │   明細 / ぎんこう / 設定        │
   └─────────────────────────────┘
            ▲
            │ 閲覧・グラフ作成
   ┌────────┴─────────┐
   │  保護者のスマホ/PC   │
   └──────────────────┘
```

### 3.3 なぜ Apps Script を挟むのか

**子どもの端末に Google の認証情報を一切持たせないため。**

Apps Script の Web アプリは「**自分(保護者)として実行**」する設定でデプロイできる。
つまりスプレッドシートへの書き込み権限はスクリプト側が持ち、
アプリ側は単なる HTTPS エンドポイントを叩くだけでよい。これにより C1 を満たす。

### 3.4 副次的な効果

- **保護者はスプレッドシートを自分のスマホで開くだけで状況を確認できる**(R2 を大きく改善)。
  子どものiPadを借りて暗証番号を入力する必要がなくなる
- スプレッドシートの標準機能でグラフが作れる。
  「貯金がどう増えてきたか」を折れ線グラフで子どもに見せられ、**教育効果としても価値がある**
- 手動バックアップの催促が実質不要になる(§9 で扱いを定義)

## 4. データ設計

### 4.1 スプレッドシートの構造

生JSONを1セルに詰め込む案は採らない。理由は2つ。

1. スプレッドシートのセルは **50,000文字が上限**で、記録が増えると破綻する
2. 人が読めないため、「保護者が閲覧する」という要件(R2)を満たせない

代わりに**正規化した3シート構成**とし、ここから状態を完全に復元できるようにする。

#### シート `明細`(おさいふの収支)

| 列 | 内容 | 例 |
|---|---|---|
| A | id | `mth1jc7iuq10w` |
| B | 日付 | `2026-09-01` |
| C | 種類 | `in` / `out` |
| D | カテゴリ | `おこづかい` |
| E | 金額 | `500` |
| F | メモ | `おてつだいのぶん` |

#### シート `ぎんこう`(口座の入出金・利息)

| 列 | 内容 | 例 |
|---|---|---|
| A | id | `mth1jd0abcde` |
| B | 日付 | `2026-09-01` |
| C | 種類 | `deposit` / `withdraw` / `interest` |
| D | 金額 | `83` |
| E | 後残高 | `10083` |

#### シート `設定`(key-value)

| キー | 内容 |
|---|---|
| `bank.balance` | 口座残高 |
| `bank.annualRate` | 年利(%) |
| `bank.lastInterestYm` | 利息の最終計算月 |
| `settings.parentPin` | 保護者の暗証番号 |
| `settings.lastBackupAt` | 最終手動バックアップ日時 |
| `_revision` | サーバ側リビジョン番号 |
| `_updatedAt` | 最終更新日時 |
| `_lastOpId` | 最後に適用した操作ID(冪等性のため) |

> **注意**: `明細` / `ぎんこう` / `設定` の3シートは同期のたびに全面書き換えされる。
> 保護者が手で書き込む場合は**別シートを作り、そこから参照する**こと。
> 書き換えはシート削除ではなく「範囲のクリア + 一括書き込み」で行うため、
> 他シートのグラフや数式の参照は壊れない。

### 4.2 アプリ側 state の拡張

既存の `state` に `sync` セクションを追加する。**この節はスプレッドシートには同期しない**
(端末固有の情報であり、同期対象にすると復元時に自分自身を上書きしてしまうため)。

```json
"sync": {
  "enabled": true,
  "endpoint": "https://script.google.com/macros/s/XXXX/exec",
  "revision": 42,
  "dirty": false,
  "lastSyncAt": "2026-09-07T09:00:00.000Z",
  "lastError": null
}
```

| フィールド | 意味 |
|---|---|
| `enabled` | 同期を使うか。未設定なら現状どおり完全ローカル動作 |
| `endpoint` | Apps Script のデプロイURL(§8 で保護者が入力) |
| `revision` | ローカルの状態が基づいているサーバ側リビジョン |
| `dirty` | 未送信の変更があるか |
| `lastSyncAt` / `lastError` | 保護者ページでの状態表示用 |

## 5. 同期プロトコル

### 5.1 API 仕様

Apps Script の `doPost` のみを使う。リクエストは `Content-Type: text/plain` で送る。

> Apps Script は `OPTIONS`(プリフライト)に応答しないため、
> **プリフライトが発生しない「単純リクエスト」にする必要がある**。
> `text/plain` はその条件を満たす。本文の中身は JSON 文字列とする。

#### `push`(アプリ → シート)

```jsonc
// リクエスト
{
  "action": "push",
  "secret": "<共有シークレット>",
  "opId": "<この送信の一意ID>",
  "baseRevision": 42,
  "payload": { "wallet": {...}, "bank": {...}, "settings": {...} }
}

// 成功
{ "ok": true, "revision": 43 }

// 競合(他端末が先に書き込んでいた)
{ "ok": false, "reason": "conflict", "revision": 45 }
```

#### `pull`(シート → アプリ)

```jsonc
{ "action": "pull", "secret": "<共有シークレット>" }

{ "ok": true, "revision": 43, "payload": { "wallet": {...}, "bank": {...}, "settings": {...} } }
```

### 5.2 スナップショット方式にすることの利点

差分ではなく**毎回すべてを送る**。記録は数年で数百〜千件程度、JSONにして 100KB 前後であり、
この規模なら差分同期の複雑さに見合わない。この選択により:

- **操作キューが不要**になる(送信順序や失われた操作を考えなくてよい)
- **再送が安全**になる(同じ内容を何度送っても結果が同じ = 冪等)
- オフライン中の変更は `dirty` フラグ1つで表現できる

### 5.3 冪等性(送信は成功したが応答を受け取れなかった場合)

トンネルに入るなどして**書き込みは成功したのに応答が届かない**ケースがある。
このときクライアントは同じ `baseRevision` で再送するため、素朴な実装では
「競合」と誤判定してしまう。

これを避けるため、各送信に一意の `opId` を付与する。
サーバは最後に適用した `opId` を `設定` シートに記録しておき、
**同じ `opId` が再送されたら、書き込まずに現在のリビジョンを返して成功とする**。

### 5.4 競合の扱い

本アプリは「子のiPad 1台が書き込む」単一書き込み者モデルを前提とする。
それでも保護者が自分の端末でアプリを開いて操作するなど、
複数端末から書き込まれる可能性はゼロではない。

競合(`baseRevision` がサーバより古い)を検知した場合、**自動では解決しない**。

- 子ども向け画面には何も表示しない(操作は継続できる)
- 保護者ページに「他の端末の記録と食い違っています」と表示し、
  **「この端末の内容で上書き」/「スプレッドシートの内容で復元」を保護者が選ぶ**

自動マージは、金額という誤りが許されないデータで意図しない結果を生むため採用しない。

### 5.5 同期のタイミング

| 契機 | 動作 |
|---|---|
| データ変更時(`saveState()`) | `dirty = true` にし、**5秒デバウンス**で push |
| アプリを閉じる/バックグラウンド化 | `dirty` なら `keepalive` 付きで push(応答は待たない) |
| アプリ起動時 | `dirty` なら push。ローカルが空なら pull(§5.6) |
| 保護者ページの「今すぐ同期」 | 即時 push |
| 失敗時 | 指数バックオフで再試行(5秒 → 30秒 → 5分)。上限到達後は次の契機まで待つ |

### 5.6 復元(pull)の安全規則

> **既存のローカルデータに対して、自動で pull を上書き適用してはならない。**

未送信の記録が失われる危険があるため、pull を適用するのは次の2ケースのみとする。

1. **ローカルが完全に空**のとき(新しい端末・ストレージ消去後)→ 自動で復元
2. 保護者が明示的に「スプレッドシートから復元」を選んだとき → 確認ダイアログの上で復元

## 6. 画面への追加(保護者ページ)

新しく「データの同期」カードを設ける。**子ども向けの画面には一切変更を加えない。**

| 要素 | 内容 |
|---|---|
| 同期の状態 | `有効 / 無効 / エラー` |
| 接続先URL | Apps Script のデプロイURLを入力する欄 + 「接続テスト」 |
| 最終同期日時 | `2026-09-07 18:00`。7日以上前ならオレンジ色で警告 |
| 未同期の変更 | `あり / なし` |
| 直近のエラー | 失敗している場合のみ内容を表示 |
| 操作ボタン | `今すぐ同期` / `スプレッドシートを開く` / `スプレッドシートから復元` |

## 7. セキュリティ設計

### 7.1 中心的な論点:エンドポイントURLは「鍵」である

Apps Script を「全員(匿名を含む)」でデプロイすると、
**そのURLを知っている人は誰でも読み書きできる**。つまり URL 自体が実質的なパスワードになる。

ここで**重大な設計上の注意**がある。

> アプリを GitHub Pages で**公開**する場合、HTMLにURLを直接書き込むと
> **ソースを見た誰でもデータにアクセスできてしまう。**

### 7.2 対策:URL をソースコードに埋め込まない

**接続先URLはHTMLに書かず、保護者が保護者ページで一度だけ入力し、`localStorage` に保存する。**

これにより、公開されたHTMLには認証情報が一切含まれなくなる。

- 保護者はURLを自分のパスワード管理ツールやメモに控えておく
  (ストレージが消えた場合、再入力が必要なため)
- URLは他人に共有しない。扱いはパスワードと同じ

### 7.3 多層的な防御

| 層 | 内容 |
|---|---|
| URLの秘匿 | ソースに含めない(7.2) |
| 共有シークレット | リクエスト本文にも合言葉を入れ、URLだけの推測アクセスを弾く |
| 保存内容の限定 | 金額・カテゴリ・メモのみ。氏名や連絡先など個人を特定する情報は保存しない |
| 排他制御 | Apps Script の `LockService` で書き込みの競合を防ぐ |

### 7.4 残存リスクの評価

URLが漏れた場合、第三者が子どものおこづかい記録を閲覧・改ざんできる。
ただし保存されるのは**金額とカテゴリのみで個人を特定する情報を含まない**ため、
影響は限定的である。家庭内利用における実際のリスクは低いと判断するが、
**「URLはパスワードと同等」という点は保護者に明示する**必要がある。

## 8. 保護者の初期設定手順(想定)

一度だけ、約10分の作業が必要になる。**これが本方式の主なコスト**である。

1. Google スプレッドシートを新規作成する
2. メニューの「拡張機能 → Apps Script」を開き、提供するスクリプトを貼り付ける
3. 「デプロイ → 新しいデプロイ → ウェブアプリ」を選ぶ
   - 次のユーザーとして実行: **自分**
   - アクセスできるユーザー: **全員**
4. 認証を求められるので承認する
   - 自作スクリプトのため「このアプリは確認されていません」と警告が出る。
     「詳細 → (プロジェクト名)に移動」で進む(正常な手順)
5. 表示された `/exec` で終わるURLをコピーする
6. アプリの保護者ページ →「データの同期」にURLを貼り、「接続テスト」を押す

## 9. 既存機能への影響

| 既存機能 | 変更方針 |
|---|---|
| 手動バックアップ(JSON/CSV) | **残す。** 同期先(保護者のGoogleアカウント)に問題が起きた場合の最後の砦 |
| 30日バックアップ催促バナー | 同期が正常なら**催促しない**。同期が7日以上失敗している場合のみ表示する |
| 利息計算 | 変更なし。計算は従来どおり端末側で行い、結果が同期される |
| 保護者ページの閲覧機能 | 変更なし(スプレッドシートでも見られるようになるが、機能は残す) |
| 暗証番号ロック | 変更なし |
| オフライン動作 | 変更なし |

### 9.1 後方互換とロールバック

- `sync.enabled` が false または未設定なら、**現在とまったく同じ完全ローカル動作**になる
- したがって不具合が起きた場合は同期を無効にするだけで元に戻せる
- 既存の `localStorage` データはそのまま使われ、移行作業は不要
  (同期を有効にした時点で、初回 push によりシートへ全件が複製される)

## 10. リスクと限界

| リスク | 影響 | 対策 |
|---|---|---|
| 保護者がスクリプト/シートを削除した | 同期が静かに停止する | 保護者ページに最終同期日時を表示し、7日以上前なら警告 |
| エンドポイントURLの漏洩 | 第三者が閲覧・改ざん可能 | §7。個人情報は保存しない |
| URLを控え忘れ、ストレージも消えた | 同期先に再接続できない | 手順書でURLの保管を明示。手動バックアップも併用 |
| Apps Script の実行上限 | 到達しない見込み | 1日あたり数十回の同期では上限に対して十分小さい |
| 複数端末からの同時書き込み | データの食い違い | 競合検知(§5.4)。自動マージはしない |
| Google 側の仕様変更 | 将来的に同期が停止する可能性 | 手動バックアップを残しておくことで最終的なデータは守られる |

### 10.1 この方式で解決しないこと

- **リアルタイム同期ではない**(数秒の遅延がある)
- **複数端末での同時利用には向かない**(単一書き込み者を前提とする)
- 保護者のGoogleアカウントに依存する(アカウント喪失時は手動バックアップに頼る)

## 13. まとめ

- 要望どおり Google スプレッドシートを保存先にするが、**唯一の保存先にはしない**。
  `localStorage` を正とし、シートを常時複製される鏡とするハイブリッド構成を採る
- Apps Script を挟むことで、**子どもに Google ログインをさせずに**保護者のシートへ書き込める
- スナップショット同期とすることで、操作キュー・順序制御・部分適用といった
  複雑さを排除し、再送しても壊れない設計にできる
- 副次的に、**保護者が自分のスマホから確認でき、貯金の推移をグラフ化できる**ようになる
- 主なコストは保護者の初回セットアップ(約10分)と、
  エンドポイントURLをパスワードとして扱う運用
